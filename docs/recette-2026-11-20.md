# Recette locale du 20 novembre 2026

Recette fonctionnelle complète de Lexia sur un Mac, dans un navigateur (navigateur intégré de l'application Claude), sur `main` au commit **`42a1cfe`** (« Decision D111 : CGU jointes a la confirmation du contrat... »). Rapport seulement : aucune correction de code.

## Conditions de l'essai

| Élément | Réglage |
|---|---|
| Code testé | worktree `claude/recette-2026-11-20` créé sur `42a1cfe`, sans modification |
| API | `api.main:create_app()` sur le port 8000, lancée par un petit lanceur hors dépôt (voir ci-dessous) |
| Site | `vite --port 5173` (mode développement, `/api` relayé vers le port 8000) |
| Base de comptes | SQLite temporaire (`APP_DB`) dans le dossier de travail de la session, **supprimée à la fin** ; jamais la base du serveur |
| Index | `data/index` du dépôt principal, lien en lecture seule (ouverture `mode=ro`) |
| Cours récupérés | `catalogue.json` (1 149 fiches) copié depuis le worktree `cours-libres`, supprimé à la fin |
| Modèle | clé Gemini locale présente (jamais affichée) : `gemini-3.5-flash-lite` et secours Gemini ; Groq désactivé |
| E-mails | le code n'a pas de mode développement (sans `RESEND_API_KEY`, la vérification d'adresse est désactivée et « mot de passe oublié » n'envoie rien). Le lanceur met une clé factice et remplace `api.courriel.envoyer` par une écriture dans un fichier local ; tout appel à `resend.com` ou `stripe.com` est bloqué. Aucun e-mail n'est parti |
| Paiement | clés Stripe factices pour activer les routes `/paiement` (dont la rétractation) ; aucun appel à Stripe. Un achat a été inséré directement en base, un second simulé par un webhook signé localement |
| OCR | Tesseract et pdftoppm installés sur le Mac |

Lanceur : seules les variables `GEMINI_*`, `EMBED_*`, `QUERY_EXPANSION_*`, `RERANK_MODEL`, `LLM_TIMEOUT_SECONDS`, `CONTACT_EMAIL` et `LEGAL_*` sont reprises du `.env` principal (lu par programme, jamais affiché). `CLE_SECRETS` est une clé neuve propre à l'essai.

### 1. Inscription (D102, D110) : OK

- Formulaire : prénom, nom, adresse, mot de passe et confirmation, case « J'ai 15 ans ou plus », case CGU et confidentialité, case facultative des e-mails d'information, menu facultatif « Comment avez-vous connu Lexia ? » (6 choix + « Je préfère ne pas répondre »). Tous les champs ont une étiquette associée.
- Envoi sans la case d'âge : refus « Cochez les deux cases ci-dessus pour créer votre compte », rien n'est créé.
- Envoi complet : redirection vers `/app`. En base : `prenom`, `nom`, `age_atteste = « 15 ans ou plus »`, `cgu_version = « 20 novembre 2026 »`, `cgu_le`, `infos_email_le`, `origine = association`.
- Avant confirmation de l'adresse : bandeau « Confirmez votre adresse e-mail pour poser vos questions » avec « Renvoyer l'e-mail » ; une question est refusée avec le même message (403). Le dépôt de cours est aussi réservé aux adresses confirmées (code relu).

### 2. Confirmation de l'e-mail : défaut D-1

L'e-mail (intercepté) contient le lien `/verifier-email#jeton=...`. Ouvert dans le navigateur où l'on vient de s'inscrire, la page affiche « Lien non valable : demandez un nouvel e-mail de confirmation », alors que l'adresse est bien confirmée en base. Deux essais, même résultat. Ouvert sans être connecté, la page affiche correctement « Adresse confirmée. Connectez-vous... ». Détail en fin de rapport.

Réutilisation d'un lien déjà servi : refus correct (« Ce lien n'est plus valable »).

### 3. Connexion : OK

Connexion par adresse et mot de passe, retour sur `/app`, titre « Bonjour, Camille. » et date du jour. Le bandeau de confirmation disparaît une fois l'adresse confirmée.

### 4. Double authentification : OK

- « Mon compte » : QR code, clé à saisir à la main, code à 6 chiffres et mot de passe ; activation, puis 8 codes de secours affichés une fois.
- Connexion : après le mot de passe, écran « Code de vérification » avec le focus dans le champ. Code faux : « Code incorrect. » et e-mail d'alerte « Lexia : code de connexion incorrect » envoyé (intercepté). Bon code : connexion. Code de secours : connexion, compteur passé à 7.
- Administration : sans 2FA, `/admin` affiche « Double authentification requise » et un lien vers `/compte?2fa`.

### 5. Suppression du compte avec le code (D110) : OK

- Le formulaire demande le mot de passe et, la 2FA étant active, le code ; le bouton reste désactivé tant que le code manque.
- Code faux : « Code incorrect. » (401), rien n'est supprimé.
- Bon code : retour à l'accueil avec « Votre compte et ses données ont été supprimés définitivement... ». En base : compte, cours, passages et sessions effacés, paiements conservés (pièces comptables), ligne d'empreinte dans `suppressions`. Les clés du navigateur propres au compte (semestre, cartes) sont effacées.

### 6. Mot de passe oublié : OK

### 7. Question de cours : OK

## Défauts classés (prêts à déléguer)

Gravité : **majeure** (parcours principal trompeur ou bloqué), **moyenne** (gêne réelle, contournable), **mineure** (cosmétique, rare ou accessibilité ponctuelle).

### D-1 (majeure) : la confirmation d'adresse affiche « Lien non valable » quand on est connecté

- Reproduire : s'inscrire sur le site (on est alors connecté), ouvrir dans le même navigateur le lien de l'e-mail `/verifier-email#jeton=...`.
- Constaté : deux `POST /auth/email/verifier`, le premier 200 (adresse confirmée en base), le second 422 ; la page affiche « Lien non valable. Ce lien n'est plus valable : demandez un nouvel e-mail de confirmation. » L'étudiant croit que la confirmation a échoué et redemande un e-mail. Sans session (autre navigateur), un seul appel et « Adresse confirmée » : c'est donc le cas le plus courant, juste après l'inscription, qui échoue.
- Cause probable : `EspaceEtudiant` monte `<AppProvider key={profil?.email ?? ''}>` au-dessus des pages publiques (`web/src/Site.tsx:198`). La page est montée avec la clé `''` pendant le chargement de la session, puis la clé devient l'adresse (fin du chargement, ou `majProfil` après la confirmation) : tout le sous-arbre est remonté, `VerifierEmail` repart avec un `useRef(false)` neuf et rappelle l'API avec le jeton déjà consommé (`web/src/site/VerifierEmail.tsx:17-31`).
- Pistes : garder le résultat hors du composant (module ou `sessionStorage` par jeton), ou ne pas mettre les pages publiques sous la clé du compte ; et côté API, accepter de nouveau un jeton déjà utilisé par le même compte confirmé (réponse « déjà confirmée »).
- Capture : `docs/recette-2026-11-20/confirmation-lien-non-valable.jpg`.

### D-2 (moyenne) : en mobile, le bouton « Mon compte » est coupé dans l'en-tête

- Reproduire : largeur 375 px, connecté, ouvrir `/compte` ou `/cours-recuperes`.
- Constaté : l'en-tête (titre sur deux lignes, menu du semestre, « 98 restantes », rond du compte) dépasse ; le rond « Mon compte » finit à 393 px pour un écran de 375 px, un bon tiers est masqué. Sur mobile, la barre du bas n'a pas d'entrée « Compte » : ce rond est le seul accès à « Mon compte » (déconnexion, 2FA, suppression, rétractation).
- Fichier probable : `web/src/components/Layout.tsx`, en-tête de l'espace (lignes 113 à 155 : menu du semestre, pastille des questions, lien `size-11` ligne 151).
- Capture : `docs/recette-2026-11-20/mobile-entete-compte-coupe.png`.

### D-5 (mineure) : la recherche de clients traite `_` et `%` comme des jokers

- Reproduire : administration, Clients, rechercher `_`.
- Constaté : les 7 comptes sont renvoyés (le `_` de `LIKE` vaut n'importe quel caractère) ; une recherche `zoe_test` trouverait aussi `zoextest`.

- Constaté : « a rembourser : rétractation (rembourser au prorata) ».

### D-7 (mineure) : l'administrateur est compté dans « Comptes » et la répartition par formule

- Constaté : avec 1 administrateur et 6 étudiants, la carte « Comptes » affiche 7 et « Gratuit 7 (100 %) », alors que l'indicateur de fidélité exclut les administrateurs. Les statistiques mélangent donc deux définitions.

- Reproduire : `/cours-recuperes?q=divorce`.
- Constaté : le menu « Matière », grisé pendant la recherche, affiche « Contentieux administratif (12) » alors que les résultats sont en droit de la famille et que la recherche porte sur toutes les matières.

- Constaté : aucun lien « Aller au contenu » sur `/app` ; au clavier depuis le haut de page, il faut traverser la navigation latérale et l'en-tête (RGAA 12.7).
- Fichier probable : `web/src/components/Layout.tsx`.

### D-10 (mineure, ergonomie) : plusieurs fichiers déposés ensemble peuvent porter le même titre

- Reproduire : déposer d'un coup `cours-contrats.pdf`, `cours-contrats.docx` et `cours-contrats.rtf`.
- Constaté : trois cours « cours-contrats » sans format ni autre indice pour les distinguer (le champ Titre n'existe que pour un fichier seul).
- Fichier probable : `web/src/components/DepotCours.tsx:58` (`sansExtension`) : garder l'extension ou numéroter les doublons.

### D-11 (mineure, juridique, à valider) : résumé vocal absent de la politique de confidentialité

- Constaté : la confidentialité ne mentionne ni le résumé vocal (D106), ni le fait que la lecture se fait par les voix du navigateur. Les voix locales sont préférées (`web/src/lib/voix.ts:14`), mais une voix « en ligne » reste sélectionnable (par exemple les voix Google de Chrome) : le texte lu part alors chez l'éditeur du navigateur.
- Fichier probable : `web/src/site/Legal.tsx` (page Confidentialité) ; éventuellement limiter le choix aux voix `localService`.

## Points à surveiller (pas des défauts constatés)

- **Case d'âge côté API** : `POST /auth/inscription` n'exige pas `age_atteste` (absent = accepté, pour les clients anciens comme l'app iOS, `api/auth.py:50` et `:344`). Seul le site impose la case ; un client qui omet le champ crée un compte sans attestation. À fermer quand l'app iOS l'enverra.
- **Formulaire de rétractation de l'e-mail** : vérifier en production que l'adresse postale et l'e-mail de l'éditeur suivent « À l'attention de Lexia » (vides en local).
- **Fidélité** : calculée sur `actif_le`, qui sert d'abord à la suppression des comptes inactifs ; la confidentialité ne cite cette donnée que pour ce motif. Usage statistique agrégé et sans donnée nominative, a priori compatible, à confirmer.
- **Semestre par défaut** : le compte neuf s'est ouvert sur « L2 · Semestre 3 », probablement repris d'une ancienne clé du navigateur de l'essai (`lexia.semestre.v1`) ; non reproduit sur un navigateur vierge.

## Non testé ou non testable

- Paiement Stripe réel (page Checkout) : clés factices ; encaissement simulé par webhook signé localement.
- Envoi réel des e-mails par Resend : e-mails interceptés localement (contenu vérifié).
- Annales : aucune en base locale (recherche « Assas » non concluante).
- Identité de l'éditeur dans les pages légales : variables `LEGAL_*` vides en local.
- Question posée sur un cours déposé (« Mon cours ») ; onglets Annales, Activité et Serveur de l'administration ; administration en mobile.
- Boîte de dialogue système du choix de fichier (fichiers injectés par script).
- Site compilé (`npm run build` servi par `api.serveur`) : l'essai a utilisé le mode développement de Vite ; D-1 ne dépend pas de ce mode (il ne se produit pas sans session, ce qu'un double appel du mode strict de React aurait aussi provoqué).

## Nettoyage

Serveurs arrêtés (ports 8000 et 5173 libres), base de test, e-mails interceptés et fichiers de cours supprimés, liens vers l'index et les modules supprimés du worktree. L'index `data/index` du dépôt principal n'a été ouvert qu'en lecture. Rien n'a été envoyé au serveur en ligne.
